## [Unreleased]

### Added (delivery-orchestrator: config wizard)
- Five commands on `deliver config`: `config explain [key|--list|--docs] [--json]` (type, allowed values, default, what it does, why it matters, which factory rule reads it), `config set <key> <json-value>` and `config unset <key>` (one validated change, no prompts, for scripts and agents), `config init [--from-draft FILE]` (create the file, optionally from an AI-written draft, then walk the keys) and `config edit [key|group] [--profile basic|factory]` (walk all keys, one group or one key). `config` and `config --write` behave as before; an unknown subcommand (a typo such as `config edti`) exits 1 with the list, and `deliver help` lists all five with their flags.
- One schema, `lib/configschema.mjs`, is the single source for prompts, `explain`, the key list and the generated key tables in `references/config.md` (between the `config-schema` markers). A parity test runs `parseConfig` and `parseLocalConfig` against every entry (accepted values, range edges, wrong types, key sets, defaults) so a change to one side only fails the build; a second test fails when the committed tables differ from `explain --docs`.
- Sensitive-change gate: keys that widen what runs unattended or weaken a gate (autonomy to L1, `merge.allow_tier3`, `checks.allow_without_ci`, shorter `protected_branches` or `hold_paths`, `local_checks`, the argv command keys `app.setup`, `app.start`, `app.stop`, `app.seed`, `tests.setup`, `tests.all`, removed `checks.required` or `verification.test_globs` entries, raised `budgets`, and others) need a typed `yes` from a person, asked once per key before the write, including values that arrive in a draft or an existing file, and any change to a sensitive key whose current value the parser rejects (it would otherwise be judged against a substitute). A first named `checks.required` list counts too (it replaces the branch-protection checks), so `init` with one asks once. `init` and `edit` need a TTY; `set` and `unset` will not loosen a rule unless a person confirms at a terminal. Tightening works from `set`. This is a guardrail for agents without a terminal, not a security boundary (a pseudo-terminal passes the TTY check and an agent can edit the JSON directly): the control is that the project file must be committed and identical to `origin/<base>` before a run, so a person reviews the diff; `--local` has no commit step and so no review.
- `edit --profile factory` walks the keys `factory run` needs and ends with a checklist of what the file alone can prove about its start refusals, plus the items that only the repository and the machine can show.
- `--local` applies `explain`, `set`, `unset`, `init` and `edit` (not `--profile factory`) to `~/.factory/config.json` (mode 0600; `wait_for_reset` is shown as unavailable while the classifier is fixtures only).
- Writes are atomic (temp file, then rename), 2-space JSON, refuse a symlinked file or folder, and refuse when the file changed since it was read. The commands never run git and touch only the config file.
- Docs: "Editing the config" in `docs/guides/delivery-orchestrator.md`, a short pointer in `SKILL.md`, wizard prose in `references/config.md`, design `docs/superpowers/specs/2026-11-23-config-wizard-design.md`, and `docs/superpowers/specs/2026-11-23-config-wizard-audit.md` (no other skill config is worth a wizard today).
- Known limits: `parseConfig` stays the authority on validity, so a new key needs a schema entry as well; `wizard.mjs` holds a few delivery-specific cross-key rules by key path (`autonomy.level`/`merge.mode`, `app.ready`, `verification.required`) and must move them behind a hook before another skill can take a copy; a file changed between the sha check and the rename can still be overwritten (a small race window); there is no repository auto-detection, so test commands, ports and CI check names come from a person or an AI draft.

### Added (feature-intake 0.1.0)
- New skill `feature-intake`: turns an idea, PRD, bug report, existing plan, experience-audit fix or growth item into one implementation-ready spec (`.product/features/FEATURE-NNN.md`, `origin: intake`) in the same contract product-intelligence specs use, so the implementer, the delivery queue and the factory read it unchanged. Design: `docs/superpowers/specs/2026-11-22-feature-intake-design.md`.
- Helper `fi.mjs`: `new` (exclusive-create ID allocation shared with the product-intelligence registry; the same `--source` returns the same ID), `validate` (frontmatter, headings, criteria grammar, dependencies and cycles, Delivery log last), `check` (readiness R1 to R9, exit 2 when valid but not ready), `approve` (user's words and name, content hash), `reopen`, `supersede` and `split` (with `## Traces`, `--rewire` for draft dependents, cycle refusal, all-or-nothing writes), `status`. Edits after approval fail with `modified_since_approval`; lifecycle edits refuse CRLF files and symbolic links.
- `SKILL.md`, references (intake procedure, writing criteria, codebase analysis, risk marking), Claude Code adapter, `docs/guides/feature-intake.md` and the routing table (intake, brainstorming, product-intelligence, implementer T0) in the guides. `npm run package:feature-intake`.
- product-intelligence's validator accepts `origin: intake` specs (contract checks only; an intake spec naming an opportunity is an error).
- Changed: a product-intelligence spec whose `origin:` is anything other than `product-intelligence` or `intake` is now a validation error (`unknown origin`).
- Known limit: a forged approval row with a recomputed hash is possible for anyone who can write the file; the factory's `criteria_hash` binding is the second line of defence.

### Added (delivery-orchestrator: factory phase 2, run control)
- P2.1 autonomy levels: `autonomy.level` `L0` (PRs only) or `L1` (merge on green) in `.product/delivery.json`, mapped from `merge.mode` when absent (a disagreement is an error; `L2` and `L3` are rejected). `--merge` is ignored only under an explicit `L0`. The template now uses `L1`.
- P2.2 hard-stop matrix `lib/hardstops.mjs`: seven rows, each with a mechanism and a proof (a test, or a saved isolation-probe result). `probe.mjs` gains FACTORY_HOME write routes and a network route, `--save`, `--from` and `--control`; proofs are bound to the target, `FACTORY_HOME` and the builder-settings sha. `factory run` prints unproven rows at start and keeps one attention row.
- P2.3 budgets: `budgets.feature.tokens/turns` (committed, default 3,000,000 and 400) and `budgets.day_tokens` (local). A feature at its cap is held `awaiting_human` with its work committed (`deliver hold --kind budget`, driver-only `deliver unhold`), without tripping the circuit breaker; `factory run --raise-budget ID[=TOKENS]` releases it. A day cap stops the run `day_budget`. Usage is recorded per repository per day under `FACTORY_HOME/usage/`.
- P2.4 interruption handling: a usage limit, timeout or stop WIP-commits (`wip(<ID>): interrupted (<kind>)`), records `f.interrupted` and resumes with a continue brief, with no fix round and no crash count; `routeInterruption` per limit kind (session, weekly, model with `fallback_model`, rate retries), waits in 30-second wall-clock slices with `caffeinate`, a monotonic session timeout and an abort poll. Local config `~/.factory/config.json` (`wait_for_reset`, `max_wait_h`, `max_wait_weekly_h`, `keep_awake`, `fallback_model`, `budgets.day_tokens`); `wait_for_reset: true` is refused while the classifier is fixtures only.
- P2.5 kill switch and locking: `factory stop [--now]`, `factory run --continue`, stop flag checked before every step, polled every 5 seconds during sessions (and by the CI wait for `--now` only) and noticed by waits within 30 seconds, kill sweep by cwd and sandbox environment, `lock.inspect`, and a convenience guard that makes interactive `deliver` refuse under a live driver lock or a pending stop.
- P2.6 attention view and status: `FACTORY_HOME/attention/<key>.md` (rows for blocked and held features, budget holds, stops and scenarios waiting for approval, each with a fixed text and the command to run; removed once the feature leaves the state), `factory status [--json]`, run state under `FACTORY_HOME/runs/`, macOS notifications with repo key, event and count only.
- Run records move to `FACTORY_HOME/records/<key>.jsonl` in driver mode and gain `tokens_by_role`, `turns_by_role`, `cost_usd_by_role`, `budget_hit`, `interruptions` and `stopped_by_user` (sticky flags); `si runs-factory --repo OWNER/NAME` reads them.
- Docs: `references/run-control.md`, spec revision 3 (reconciliation with the code as built), roadmap status. Known gaps: `stop --now` does not interrupt a verification in progress; the driver sends only the paused, stopped and finished notifications (no per-item attention notification); the network hard-stop row's tool layer is a static check; the usage-limit classifier is fixtures only, so `wait_for_reset` stays off until a real capture exists.

### Added (delivery-orchestrator: factory phase 1a, verification gate)
- Factory driver `factory.mjs` (plain Node): `factory scenarios [--only IDS]` / `--approve ID --by NAME` and `factory run [--only IDS] [--limit N]` (exit 0 done, 1 refused with fix lines, 2 stopped or a person needed). It refuses without `verification.required`, readiness level 4, empty `local_checks` and branch protection requiring `factory/verified`. Lock per repo with orphan process-group kill, crash-and-resume rules, start sweeps, attention entries. Works in a driver clone under `FACTORY_HOME/clones/` and a separate builder clone (`FACTORY_BUILDER_HOME`); commits move between them as bundles only. Live orphans or leftovers from an earlier run stop a resumed queue before any step.
- LLM roles as `claude -p` sessions with allowlisted environment and per-role settings (`core/settings/builder.json`, `author.json`); user settings outside a key allowlist (hooks, a status line or plugins included) refuse the session.
- Hidden scenarios under `FACTORY_HOME/scenarios/` (coverage lint, canary, approval bound to `scenarios_hash`, re-linted against the base spec's `criteria_hash` on every use); every API scenario needs a status assertion, and requests with refused headers or a body on GET/HEAD are lint-refused.
- Verification of the exact PR head in a `sandbox-exec` sandbox (setup, then each scenario twice from a fresh seed and start; escaped processes or a busy port refuse); verdict files `FACTORY_HOME/verdicts/<repo>/<ID>.<sha>.json`; criterion-level symptom brief; `factory/verified` status and PR body line.
- Anti-gaming checks G1-G5 at built and at merge; `deliver merge` with `verification.required` needs state `verified`, a matching verdict and clean G-checks; `deliver hold` (driver only); `retry --note` overrides an anti-gaming hold for exactly the held sha and G-ids. Run records gain verification fields.
- API benchmark fixture and runner `bench/factory/` (held-out scenarios stay local).
- References: `references/verification.md`, `references/factory-driver.md` (including the known isolation gaps: unproven deny rules and `disableAllHooks`, spoofable `factory/verified`, no secret scan before push, macOS-only survivor scan and sandbox).

### Fixed
- `install-agents.mjs` in product-intelligence, experience-audit and implementer did nothing (exit 0, no files) when run through a symlinked path, such as a symlinked skills folder or macOS `/var` → `/private/var`: the entry-point check compared an unresolved path with the resolved module path. It now compares real paths, as growth-strategy does; a test runs every skill's installer through a symlink.

### Added (delivery-orchestrator: factory phase 0)
- `deliver readiness [--repeat N] [--json]`: scores a repo from level 0 to 4 (config, tests run, CI gate, app starts with logs and seed) with a result and fix item per check, run in a temporary worktree with an allowlisted environment. The result is saved outside the repo in `~/.factory/readiness/` (`FACTORY_HOME` overrides). Exit `2` when below `readiness.min_level`. New optional config keys: `app`, `tests`, `readiness`.
- Merge gate in `deliver init`: when merging is authorised and the config has a `readiness` key, `init` refuses on a missing, stale, future-dated or config-mismatched result, or a level below `min_level` (it re-runs the cheap checks and can only lower the stored level). Repos without the key behave as before.
- Run records: every merged, skipped, blocked or awaiting-human outcome is appended to `.skill-runs/factory-runs.jsonl` (metadata only, written even with `SKILL_RUNLOG=off`), keyed by a per-run `run_id`.
- `si runs-factory` (skill-insights): joins those records to transcript tokens, subagents included, with per-run coverage and `ambiguous` rows for overlapping features; `--out` never overwrites the source log.
- Spikes: usage-limit classifier and passive capture tooling (fixtures only so far), and a rerunnable sandbox isolation probe. Notes: `docs/factory/spikes/`. Reference: `references/readiness.md`.

### Added (growth-strategy 0.1.0)
- New skill `growth-strategy`: evidence-backed organic growth strategy for independent websites and products. Roles: product-seo-auditor, search-researcher, distribution-researcher (parallel), growth-reviewer (independent); commands `init`, `audit`, `research`, `plan`, `review`, `full`, `refresh`, `status`. Design: `docs/superpowers/specs/2026-11-18-growth-strategy-design.md` (independently reviewed; resolutions recorded there).
- `.growth/` state: `growth.json` (baseline, phases, reviews, append-only decision log, refreshes, performance imports), `sources.json` (provenance with access dates and file hashes), `keywords.json` (+ `gs export keywords` CSV, formula-safe), `items.json` (roadmap candidates), six markdown artifacts with required sections, `roadmap.md` from approved items only, `handoff/GRO-NNN.md` implementer specs.
- Helper `gs.mjs` enforces: no metric value without provenance (`measured` only from imported Search Console or analytics exports, `estimate` only from tool exports or the user, otherwise `unknown`/null); sources exist and are not future-dated; no traffic numbers on roadmap items; Given/When/Then for implementer items; a hash-checked approved baseline before any phase closes; decisions only after a review bound to the current plan hash, independent by default, with Critical/High findings blocking approval; decided items superseded rather than edited; item statuses must match the decision log; review files are hash-checked and a later clean review cannot clear earlier Critical findings; writes (including native agent installs) never follow symlinks. `import gsc` keeps only aggregates and tracked-keyword metrics.
- Claude Code and Codex agents generated from the role registry; tests cover the three fixture projects (image utility, SaaS, content site), evidence rules, gates, resume, refresh, CSV export and single-skill install.

### Added (experience-audit 0.1.0)
- New skill `experience-audit`: audits a live web app in a browser for layout/UX, footer and navigation, accessibility and technical SEO. A read-only collector probe returns a JSON snapshot; deterministic checks in `ea.mjs analyze` turn it into findings (measured, rule, or capped judgment) with severity, effort and root-cause group. A ledger, decision log, ranked report, fix specs for the implementer (`ea fix`) and re-audit verification (`ea reaudit`) complete the loop. Design: `docs/superpowers/specs/2026-11-18-experience-audit-design.md`. Ledger text that is copied into fix specs and reports is validated (one line, bounded, no control characters); outputs never follow symbolic links; fix ids are validated against path traversal.

### Added (delivery-orchestrator)
- New skill `delivery-orchestrator`: works through `FEATURE-NNN.md` specs with `status: ready` one at a time (optional `depends_on`): feature branch, the implementer skill, PR, wait for CI, squash merge of the exact commit CI verified, sync the base, next. State in `.delivery/queue.json` (resumable); a helper (`deliver.mjs`) enforces the state machine and every merge precondition.
- Guard rails: merges only with `--merge` and the user's words; the run stops when the repo has no CI (`--no-ci` is explicit); T3 work and changes to CI or `CODEOWNERS` files are held for a person; capped CI fix rounds; circuit breaker; never force-push, `--admin` or `--auto`; stale head, behind and conflicting PRs handled; titles and reasons sanitised, no shell.
- `implementer --unattended` and `--name <slug>`: nothing waits for a person; every "stop and ask" case ends the run as `BLOCKED` with the question.
- Tests run a real git repo with a bare origin against a fake `gh`.
- Project config `.product/delivery.json` (`deliver config [--write]`): GitHub account (token held in memory, verified login and write access), base branch, `protected_branches` (default main, master, prod, production, release/*: never merged into, flags cannot override), standing merge mode, required and ignored CI checks, `local_checks` run by the orchestrator, `hold_paths`, limits, `implementer_notes`. The file must be committed and identical on the base branch; a feature that edits it is held.

### Added (arsenal: vendoring and bootstrap)
- `skills.lock.json` plus `scripts/skills.mjs` (`status`, `check`, `vendor`, `update`, `accept`, `bootstrap`): pinned, license-tracked vendoring with a dry-run-first `update` and a safe `bootstrap` that never overwrites unmanaged items or follows symlinks.
- Ported from the global skills, chosen by real usage: autonomous, pr-review, pr-review-orchestrator, phased-review, retro, and the deep-pr-review and pr-review commands (imported as-is). Vendored a Superpowers subset (MIT, v7.0.2, namespace rewritten): writing-plans, executing-plans, subagent-driven-development, brainstorming, finishing-a-development-branch, systematic-debugging, test-driven-development, requesting/receiving-code-review, using-git-worktrees, using-superpowers, verification-before-completion. graphify and security-audit are pin-only (external).
- Hardened against hostile upstreams and projects: `vendor`/`update` refuse symlinks anywhere on the source path and a non-regular LICENSE (validated before anything is written); project-scope `bootstrap` refuses a symlinked `.claude`, `skills`, `commands` or manifest, and writes the manifest by temp file + rename.
- Repo validator reads the lock: imported and vendored skills get spec-level checks only, and lock consistency (entries, hashes, licenses) is enforced.

### Added (run telemetry)
- `pi` and `impl` write a metadata-only run log (`.skill-runs/<skill>.jsonl`, self-ignoring; off with `SKILL_RUNLOG=off`): command, outcome, duration, ids and counts, never prompts, code or free text. `impl` records tier, input spec id, plan size, fix rounds, blocked tasks, rulings count.
- New `retro` command on both helpers: a short agent self-report (unclear / skipped / improvised / suggest) logged at the end of a run.
- `si export` (skill-insights 0.2.0): one redacted bundle per project (run summaries, self-report, transcript cost) to bring back for skill improvement. Structural fields are allowlisted, free text is redacted (paths, emails, URLs, secrets, token shapes), `--no-notes` drops the self-report, `--out FILE` writes it owner-only without following symlinks. Run-log writes never follow symlinks; `verify-clean` ignores only our own root `.skill-runs/*.jsonl` (and tracked files always count).

### Added (skill-insights 0.1.0)
- New skill `skill-insights`: read-only analyzer over Claude Code transcripts. `si inventory` (real usage per skill, installed-but-unused), `si runs`, `si report` (tokens, wall time, tool errors, repeated reads, large outputs per skill). Detects both model-invoked and slash-command skill runs. Output is redacted: no paths, project names or message text.

### Added (run modes)
- `widen` modifier: broader competitor reach (`research.widen_competitor_multiplier`), new source types, a second discovery pass targeting `research.widen_target_candidates` candidates examined. Admission test and confidence caps unchanged.
- `override` modifier: rerun regardless of freshness; approvals are not reset. (Freshness was never enforced in code; the agent could mistake fresh research for "nothing to do".)
- `full auto`: unattended run with a confidence review per phase, `.product/attention.md` queue, one final report and decision sheet. Gate 1 can be approved by recorded delegation (`approve-product --delegated --note`, shown in `pi status` as `approved_by_delegation`); opportunity decisions are never delegated and the helper refuses `--delegated` anywhere else. Controlled by `gates.allow_delegated_approval` (default true); `human_confirmation: tty` still requires a person.

### Fixed (third independent review)
- `gates.human_confirmation: "tty"` now works from a real terminal (the earlier build never accepted "yes"); it is documented as a deterrent, not a boundary.
- `decide` refuses to append to a Decision Log that already fails its integrity check, so a damaged log cannot be made to look legitimate.
- Each decision seals a digest of the opportunity (title, scores, detail block) in a new `Content` log column; rewriting an approved idea is detected. Logs written before this change must be regenerated.
- `decision_count` is a required frontmatter field; superseded specs are validated for linkage only; `new-feature` and the Ready transition require an unmodified baseline.
- Evidence sources are canonicalised (path and URL aliases count once; `.product/` and `.git/` never count).
- Stray Revision History rows, a hand-edited `last_reviewed`, quoted or U+2028 names, symlink retargeting, the `last_research: never` template value, and note validation order are fixed.
- Docs: `pi snapshot` at the start of every run, `--discard` in help, accurate list of commands that refuse without an approved baseline.

### Fixed (second independent review)
- Decision Log: row count and head seal are kept in the frontmatter, so truncating the log or hiding rows behind a gap is detected.
- `verify-clean`: tracked files are never excluded (even under `build/`, `dist/`, `target/`), file permissions are hashed, more bulk folders are skipped for untracked files only.
- Confidence cap counts only primary sources (https or an existing repo file); `search:`/`ref:` can only back low-confidence facts.
- `decide` and `transition ... Proposed` require an approved, unmodified PRODUCT.md; approval metadata must match the Revision History.
- Approved items can be reversed by the user (spec marked `superseded`); `confirm-product` re-confirms a stale baseline without a new revision.
- Validator reports stray files in `features/`, rubric changes, malformed history rows; rating names may contain digits; pipe escaping and private-host checks corrected.
